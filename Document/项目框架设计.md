# 《地穴行者》(CryptWalker) 项目框架设计（缩略版）

> 2D 正俯视角 · 动作肉鸽 · 单人 8 周毕设
> 架构基础：双程序集热更（Main AOT + HotUpdate 热更）· HybridCLR 代码热更 · YooAsset 资源管理
> 设计原则：**取其神、去其形** —— 保留工业级架构骨架，砍掉多人协作型重模块

---

## 〇、设计取舍总览

参考商业项目框架后，对毕设规模做出的取舍：

| 商业项目模块 | 毕设处理 | 理由 |
| --- | --- | --- |
| 双程序集 + HybridCLR | ✅ 全留 | 已跑通，最大技术亮点 |
| 轻封装、重编排哲学 | ✅ 全留 | 架构灵魂 |
| 桥接 IAppBridge | ✅ 全留 | 热更纪律根基 |
| PureMVC 框架 | 🔄 换轻量 MVC | 保留三层解耦思想，去框架负担（见 3.1） |
| Excel→JSON→SO 流水线 | ❌ 砍 | 数据量小，无策划协同 |
| UniTask + CancellationToken | ❌ 砍 | 标准 async/await 够用 |
| ListView 虚拟列表 / GenMVC | ❌ 砍 | UI 简单 |
| 网络模块 | ❌ 砍 | 单机 |
| 对象池 | ✅ 保留 | 肉鸽高频实例化必备 |
| FSM + 配置化 AI | ✅ 保留 | 策划案 5.3 已定 |
| 三层 catch / 日志规范 | ✅ 保留（简化） | 答辩亮点 |
| 引用计数句柄 | ⚠️ 简化 | 缓存字典够用，遇泄漏再上 |

**一句话**：商业项目证明的是"多人协作怎么活下来"，毕设只需要"一个人做完还讲得清"——留骨架、砍协作负担。

## 一、双程序集架构（已有，保持）

### 1.1 Main（AOT 主工程，不可热更）—— 保持轻薄
职责：启动编排、桥接、资源/热更装载、平台 API。打包后不能改。

### 1.2 HotUpdate（热更业务）—— 99% 代码在这
职责：全部游戏业务。可发补丁热更，逻辑可替换。

### 1.3 启动链路（已跑通）
```
MainLauncher.Start()
  ├─ new AppBridge()                    # 造桥：热更侧唯一 AOT 通道
  ├─ YooAssetService.InitializeAsync()  # 资源服务（失败降级）
  └─ TryBootHotUpdate()
       ├─ 加载 AOT 补充元数据（HybridCLR）
       ├─ Assembly.Load 热更 dll
       ├─ 反射调用 GameRoot.Run(bridge)
       └─ 收取 OnUpdateTick → 每帧驱动
```

### 1.4 边界纪律
- Main 不依赖 HotUpdate 具体类型（只依赖接口）
- 热更侧禁止直接 new Main 类型，一律走 `IAppBridge`

## 三、核心机制设计

### 3.1 MVC 轻量分层（不用 PureMVC，但保留 MVC 解耦）
**目标**：不引 PureMVC 框架（Facade/Mediator/Proxy/Command 四件套 + 字符串 Notification），但保留 **Model / View / Controller 三层职责分离**，模块间靠事件解耦。

**三层在本项目的落地**：

| 层 | 职责 | 本项目实现 |
| --- | --- | --- |
| **Model**（数据） | 持有数据，只增删改 | `DataService` + 业务数据类（PlayerData / WeaponSlot / BuffList / RoomData） |
| **View**（表现） | 只负责显示，不碰数据逻辑 | `UIViewBase` / `UIManager` / 各 UI 面板 |
| **Controller**（逻辑） | 操作 Model，驱动游戏流程 | 各系统 Manager（GameFlowMachine / CombatSystem / BuffSystem / RoguelikeGen） |

**解耦规则（红线）**：
```
View        ──订阅事件──► EventBus ◄──发事件──  Controller（操作 Model 后广播）
View 不直接改 Model；Controller 不持 UI 引用；两者只通过 EventBus 通信
```

**代码示例（以伤害为例）**：
```csharp
// Model：伤害计算（CombatSystem/Controller 调用，结果广播）
EventBus.Raise(GameEvent.PlayerDamaged, new DamageInfo(amount, sourceDir));

// View：HUD 订阅事件刷新，不关心谁打的
EventBus.Subscribe(GameEvent.PlayerDamaged, data => hpBar.fillAmount = player.Hp / player.MaxHp);
```

**为什么不用 PureMVC**：注册表 + 字符串通知 + 四件套对单机单人项目是负担；轻量 MVC 用枚举事件 + 直接类引用，保留同样的解耦效果，代码量少一个数量级。

### 3.2 事件中心 EventBus（MVC 的通信总线）
```csharp
public enum GameEvent { PlayerDamaged, EnemyDied, BuffChosen, WeaponSwitched, ... }

EventBus.Instance.Raise(GameEvent.EnemyDied, enemy);
EventBus.Instance.Subscribe(GameEvent.EnemyDied, OnEnemyDied);
```
枚举防写错字符串，是 3.1 三层之间唯一的通信通道，单机够用。

### 3.3 状态机 FSM
**流程机**（已有 `GameFlowMachine`）：Boot → MainMenu → Game → Settle，扩展即可。
**敌人 AI**（策划案 5.3）：同模板，状态 = Idle/Patrol/Chase/Attack/Hit/Death，转换表预留 JSON 配置位（答辩点：配置化 AI）。

### 3.3 对象池（策划案 8 章）
```csharp
public interface IPoolable { void OnSpawn(); void OnRecycle(); }
public class ObjectPool<T> where T : MonoBehaviour, IPoolable { /* 取用/归还，超上限销毁 */ }
```
池对象：普通敌人 / 精英 / 玩家弹道 / 敌人投射物 / 伤害数字 / 拾取物 / 特效。

### 3.5 配置驱动（已有，延续）
SO 配置 + `DataService` 按 `asset://data/{folder}/{id}` 加载缓存。武器/敌人/Buff/遗物/道具各建 SO 子类，不加 Excel 层。

### 3.6 异步
标准 async/await，沿用 MainLauncher 模式（`await YooAssetService`、`await DataService.GetAsync<T>()`）。不引 UniTask。

### 3.7 错误处理与日志
```csharp
catch (OperationCanceledException) { }          // 取消静默
catch (BusinessException e) { /* Toast */ }     // 业务提示
catch (Exception e) { Log.Error(e); }            // 未知上报
```
日志统一走 `GameRoot.Bridge.Log()`，实现 `Log` 静态类包一层。

### 3.8 UI 框架（轻量）
`UIManager` + `UIViewBase` 两个类：打开/关闭 + 层级（HUD / 弹窗 / 加载）。不做虚拟列表、ViewBinder、Mediator。

### 3.9 模块化设计（IModule + 模块清单）
**原则**：单机毕设也要模块化，但用"管理器（Manager）"而非 MVC 的 Model——Model 管数据，Manager 管一类能力（如 UI/音频/池）。MVC 视角下 Manager 属于 Controller 层。

**公共接口**：
```csharp
public interface IModule
{
    void Init();          // 游戏启动时统一调用
    void Shutdown();      // 退出/切场景时清理（可选）
}
```

**模块清单**：

| 模块 | 职责 | 状态 |
| --- | --- | --- |
| `UIManager` | 打开/关闭/层级/栈 | 设计 |
| `AudioManager` | BGM/SFX 双通道 + 音量持久化 | 设计 |
| `PoolManager` | 对象池统一入口 | 设计 |
| `DataService` | 配置加载缓存 | 已有 |
| `EventBus` | 事件通信 | 设计 |
| `GameFlowMachine` | 流程状态机 | 已有 |

**管理方式**（手动列表，不用反射注册表）：
```csharp
public static class Modules
{
    public static UIManager    UI    = new UIManager();
    public static AudioManager Audio = new AudioManager();
    public static PoolManager  Pool  = new PoolManager();

    public static void InitAll()   // GameRoot.Run() 按依赖顺序调
    {
        Pool.Init();      // 1. 池最先（UI/音频可能用到）
        UI.Init();        // 2. UI
        Audio.Init();     // 3. 音频
    }
}
```

**UIManager 层级设计**：
```csharp
public enum UILayer { HUD, Normal, Popup, Loading }

// 场景 Canvas 下预设 4 个 root，各挂 Canvas 组件设 sortingOrder：
// HUD=0, Normal=100, Popup=200, Loading=300
// Open() 时 Instantiate 到对应 root 下，SortingOrder 天然分前后
```
弹窗永远盖住 HUD，Loading 永远最顶。`_stack` 记录打开顺序支持返回。

## 四、设计纪律（红线）

| 纪律 | 说明 |
| --- | --- |
| 热更侧禁止直接 new Main 类型 | 一律走 `IAppBridge` |
| 业务禁止直接调 YooAsset | 走 `DataService` / `YooAssetService` 封装 |
| 敌人 AI 转换表预留 JSON | 答辩点：配置化 AI |
| 高频对象必须走对象池 | 弹道/敌人/伤害数字/特效 |
| 模块间用 EventBus，不互相持引用 | 保持可替换 |
