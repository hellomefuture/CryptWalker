# 技术难点与解决过程（面试用）

> **用法**：每条开头都有一个「30 秒版」，面试时先甩这句；面试官追问了再往下讲。
> **主推顺序**：① GridGraph 平面问题 → ② 惩罚代替排除 → ③ UGUI 每帧写 UI。
> 这三个故事性最强，而且都能体现**"怎么定位"**，而不只是"用了什么 API"。

---

## 〇、先背这三个数字

面试时说出具体数字，可信度完全不一样：

| 数字 | 含义 |
| --- | --- |
| **8541** | A\* 插件图的节点总数（117×73 的包围盒） |
| **1587** | 真正可走的格数（从地板 Tilemap 反查出来的权威值） |
| **5183** | 出错时插件报的可走数 —— **既不等于 8541 也不等于 1587**，这个"两头不靠"就是错位的指纹 |

## 一、敌人"卡墙"：GridGraph 默认铺在 XZ 平面

**30 秒版**

> 换了 A\* 插件之后敌人开始撞墙卡住。我没靠猜 —— 我在"可走性校正"那一步加了一条**等值断言**：插件图的可走节点数必须等于我用地板反查出来的权威值。结果它打出 `5183/8541`，**既不等于总数 8541，也不等于权威值 1587**。这个"两头不靠"本身就是指纹：说明节点和地板没落在同一片空间上。顺着查下去发现，`GridGraph` 是为 3D 设计的、**默认铺在 XZ 平面**，节点的 `world.y` 恒等于 0 —— 8541 个节点全挤在同一行上查可走性，可走性彻底错乱，于是 A\* 根本不知道墙在哪，直接走直线撞墙。加一行 `is2D = true` 解决。

**现象**
- 敌人走一段就贴住墙、顿一下，然后靠已有的"侧向脱困"自己挤出来（"卡一小会就好了"）
- 编辑器里表现是"看着有点笨"，**不报任何错** —— 这类 bug 最难定位

**怎么定位的（这条是重点）**

我在 `ApplyWalkabilityFromNavGrid` 里加了一行自检日志：

```csharp
// 校正后插件的可走数，应当与 NavGrid（地板反查出来的权威数据）完全相等
string verdict = alignedTrue == navGrid.WalkableCount ? "✓ 一致" : "✗ 不一致！";
Core.Log.Info($"[Astar] 校正自检：与地板对齐 {alignedTrue}（NavGrid 权威值 {navGrid.WalkableCount} {verdict}）");
```

打出：

```
[Astar] 校正自检：与地板对齐 5183（NavGrid 权威值 1587 ✗ 不一致！）
```

**为什么这个数字有意义**：如果只是"格子整体偏移一格"，可走数仍然会是 1587（只是错位的位置）✗；
如果完全没生效，会是 8541。**5183 说明 8541 个节点被映射到了少数几个格子上** —— 典型的"坐标在某一个维度上塌陷"。

顺着这个方向去读插件源码，`GridGenerator.cs:704` 的注释直接把答案写着了：

```
In graph space all nodes are laid out in the XZ plane
```

**根因**

`GridGraph` 是给 3D 场景设计的（横放的 XZ 平面）✗ → 节点坐标是 `(x, 0, z)` ✗
→ 而我是 2D（XY 平面）✗ → 拿 `node.position` 去查地板格时，**y 永远是 0**
→ 8541 个节点全落在 `y=0` 那一行上 ✗ → 可走性数据彻底无意义 ✓

**解决**

```csharp
gg.is2D = true;   // 必须最先设：图落到 XY 平面，节点坐标才能和地板格一一对应
```

**修好后的验证**（三个数字同时对上，这就是"修对了"的证据）：

```
[Astar] 校正自检：范围内节点 5141；与地板对齐 1587（NavGrid 权威值 1587 ✓ 一致）；改动 6954 个

5141 = NavGrid 的格子总数        → 图和地板严丝合缝重叠
1587 = NavGrid 的可走格数        → 可走性完全一致
6954 = 8541 − 1587               → 每个节点都被正确校正
```

**追问准备**

| 面试官可能问 | 怎么答 |
| --- | --- |
| 你怎么知道是插件的错，不是你的错？ | "我不知道。所以我先加了一条'两边必须相等'的断言，让数据告诉我谁错了 —— 而不是靠读代码猜。" |
| 如果没有那条自检，你会怎么查？ | "会难很多，大概会去怀疑碰撞体尺寸、怀疑移动代码。这件事之后我把'关键数据加等值断言'变成了习惯。" |
| 为什么一开始会漏掉 `is2D`？ | "插件默认值是面向 3D 的，而我的项目是 2D。**'默认值恰好适应我的场景'是小概率事件**，这是这轮的教训。" |

## 二、修一个问题引入新问题：从"排除贴墙格"改成"给贴墙格加惩罚"

**30 秒版**

> 敌人贴墙走的时候，碰撞体边缘正好擦着墙面，物理引擎一直把它往外推，表现就是"卡一小会、然后脱困"。我第一版的做法是把贴墙的格子设成**不可走** —— 结果**把走廊整条堵死了**，房间之间不连通，敌人跨不了房间。原因是我们走廊是 3×3 的矩形：里面铺满地板，但两条长边各铺一排墙，**可走横截面只剩中间 1 格**，而它的上下邻接都是墙，被判成"贴墙"就整条废了。最后改成**加惩罚**：插件文档写明 `1000 = 多走一格的代价`，于是房间内 A\* 会为了省这 1000 主动走中间，而走廊绕不开就照走 —— 两边都保住了。

**现象**
- 敌人贴墙走时一顿一顿（"卡一小会就好了"）
- 第一版修复后：可走数从 **1587 掉到 1167** —— 少了 420 个

**怎么发现的**

就是上面那个自检数字 ✗：改完之后 `1587 → 1167` ✓

我没停在"看起来不卡了"，而是去核对了这 420 个是什么 ✗ → 顺手读了一遍走廊生成代码，发现：

```
3×3 的走廊矩形里【铺满地板】，然后【两条长边各铺一排墙】
→ 可走横截面只剩中间 1 格（上下都是墙）
```

⚠️ **这 420 里包含全部走廊** ✗ → 房间之间不连通 ✗

（这一点当时在游戏里**没暴露** ✗ —— 因为同房间战斗走的是"有视线就直冲"那条快路径，不需要走廊。**是数字先发现的，不是眼睛**。）

**根因**

"贴墙"这件事有两种表达方式，我第一版选错了 ✗：

| 做法 | 效果 |
| --- | --- |
| 设为**不可走** ✗ | 房间里 A\* 确实不贴墙了 ✓ 但走廊也被堵死 ✗ **连通性被破坏** ✗ |
| 加**惩罚** ✓ | 房间内"能绕就绕" ✓ 走廊"绕不开照走" ✓ **连通性不受影响** ✓ |

**解决**

```csharp
// 插件文档（GraphNode.cs:70）：1000 = 多走 1 世界单位的代价，也就是【= 多绕一格的代价】
private const uint WallHugPenalty = 1000;
...
n.Walkable = aligned;                              // 可走性仍然以地板为准
n.Penalty  = hugWall ? WallHugPenalty : 0u;        // 贴墙只是"变贵"，不是"不可走"
```

**已实测确认（运行时日志，重跑一局后）**

两行自检同时打出来（`seed=80`，6 间房）：

```
[Astar] 校正自检：范围内节点 5141；与地板对齐 1587（NavGrid 权威值 1587 ✓ 一致）；改动 6954 个
[Astar] 贴墙惩罚：420 格 +1000（≈多绕一格的代价）—— 房间内能绕就绕（不擦墙），走廊绕不开照走
[Astar] 扫描完成（236 ms，主线程一次做完），可走节点 1587/8541
```

| 现象 | 对应判据 |
| --- | --- |
| 敌人能跨房间走过来（走廊连通 ✓） | **`与地板对齐 1587 == NavGrid 权威值 1587`** ✓ —— 走廊那 1 格必须还在图里。早先"设为不可走"的版本这里是 **1167** ✗（少的 420 格 = 全部走廊 ✗） |
| 仍不擦墙 ✓ | `贴墙惩罚：420 格 +1000` ✓ —— 那 420 格**没有被删掉，只是变贵** ✓ 所以房间内 A\* 主动绕开 ✓ |

⚠️ **关键一点（面试时值得主动讲）**：
**光有"不擦墙"并不能证明第二版是对的** ✗ —— 第一版（直接排除贴墙格）同样"不擦墙" ✓，却把走廊堵死了 ✗。
能区分两者的**只有可走数** ✓ —— 这正是"**改完必须回核被保护的不变量**"的由来 ✓
（换个说法：**症状消失了不等于修对了** ✓）

**追问准备**

| 面试官可能问 | 怎么答 |
| --- | --- |
| 怎么保证惩罚值合适？ | "刻度是插件文档给的，1000 = 多走一格。所以这个值在语义上是'我愿意多绕一格来换不贴墙'，可解释、可调。" |
| 走廊还是只有 1 格宽，不会卡吗？ | "会窄，但不擦墙 —— 因为中路那一格离两侧墙面各 0.5 格以上，而敌人碰撞体半径约 0.5 格，正好不接触。" |
| 这一轮最大的收获？ | "**修 bug 之前要明确'什么被保护'**。我第一版只想着'让路径别贴墙'，忘了'不能破坏连通性' —— 后者优先级更高。" |

## 三、"Loading 之后一直卡"：UGUI 每帧写 UI 触发 Canvas 重建

**30 秒版**

> 加载界面用过之后，游戏一直卡。原因是我的 `LoadingScreen.Update()` 无条件每帧执行，每帧都在做两件事：一是用 `$"{pct}%"` **拼字符串**（每帧产生垃圾），二是给 `sizeDelta` / `anchoredPosition` **赋同一个值** —— 而 UGUI 里**赋同样的值也会把元素标脏，触发整张 Canvas 重建**。更要命的是界面隐藏之后它**照样在跑**。修法是两道：隐藏后把整个 Canvas `SetActive(false)`，以及渲染前做**变化检测**（百分比整数没变就不写、宽度没变就不碰 RectTransform）。"Loading 之后"这个时间点本身就是线索 —— 说明问题出在加载界面**用完之后**，而不是加载本身。

**现象**
- 刚开始没事，一旦经过加载界面（进战斗）之后就持续掉帧

**定位的关键：从"时间点"推责任方**

"**Loading 之后**"这个词很关键 ✓ —— 说明问题不是"加载中"，而是"加载完之后"

→ 那么"加载完还在持续运行的东西"就是嫌疑 ✗
→ 加载界面的 `Update()` 隐藏后仍然每帧执行 ✗ → 命中 ✓

**根因（两条，都是 UGUI 的经典坑）**

```csharp
// 旧代码：每帧无条件执行
_percentText.text = $"{_progress * 100f:0}%";   // ① 每帧分配一个字符串 → GC 垃圾
_bar.sizeDelta = size;                          // ② 赋同样的值也会标脏 → Canvas 重建
_bar.anchoredPosition = pos;                    //    整张 Canvas 每帧重算
```

② 是重点：**UGUI 的脏标记不比较值** ✗，只要走了一次 setter，它就把整个 Canvas 标记为需要重建 ✓

**解决**

```csharp
// ① 隐藏后整个 Canvas 关掉，零开销（不只是 alpha=0）
if (!_visible && _fadeOutAt < 0f)
{
    if (_canvasGo != null && _canvasGo.activeSelf) _canvasGo.SetActive(false);
    return;
}

// ② 变化检测：值没变就不碰 UI
int pct = Mathf.RoundToInt(_progress * 100f);
if (_percentText != null && pct != _lastPct) { _lastPct = pct; _percentText.text = pct + "%"; }
```

**追问准备**

| 面试官可能问 | 怎么答 |
| --- | --- |
| UGUI 为什么赋值会重建？ | "UGUI 靠脏标记驱动重建。setter 里不比较新旧值，只要调用就标脏，所以'赋同样的值'和'真的改了'代价一样。" |
| 那你为什么不用 `SetActive(false)` 直接关物体？ | "我就是这么做的。但只在'完全隐藏后'做 —— 淡出过程中需要 Update 继续跑，所以判断条件是 `!visible && 淡出已结束`。" |
| 还有别的 UGUI 性能点吗？ | "`SetActive` 比 `alpha=0` 好（前者不参与布局和重建）；Text 换成 TMP；避免布局组每帧刷新；拆 Canvas 隔离重建范围。" |

## 四、把抖动挪到玩家看不见的地方：加载界面里的主动 GC

**30 秒版**

> GC 一定会发生，问题只是"什么时候抖"。与其让它随机落在战斗中途造成掉帧，不如主动选择时机 —— 在加载界面盖着屏幕的时候做 `GC.Collect()`，玩家看到的是进度条，抖动被藏在画面里。另外我特意把 `Resources.UnloadUnusedAssets()` 单独做成开关并**默认关闭**：它会把"没有任何强引用"的资源卸掉，万一战斗要用的贴图恰好只被短暂引用过，就会被卸掉然后**每帧重新加载**，比不卸载更卡。

**做法**

```csharp
System.GC.Collect();
System.GC.WaitForPendingFinalizers();   // 终结器队列里的对象也清掉
System.GC.Collect();
if (unloadAssets) Resources.UnloadUnusedAssets();   // 默认关：风险最高的一步单独隔离
```

判定"什么时候做"用的是加载界面的时序规则：
**进度必须走到 100%（没到就补满）+ 至少显示 1.5 秒 + 到 100% 后再停 0.4 秒 → 才开始淡出并 GC**

**追问准备**

| 面试官可能问 | 怎么答 |
| --- | --- |
| 主动 GC 不是会更卡吗？ | "单次更贵，但时机可控。**随机的小抖动累积起来比一次可控的大抖动更伤体验**。" |
| 为什么 `UnloadUnusedAssets` 默认关？ | "它会卸掉'没有强引用'的资源。我不想让一个我无法完全预测其引用的 API 默认生效 —— 先只做托管 GC，要压内存时再打开，并确认打开后没变卡。" |
| 那怎么知道资源有没有泄漏？ | "结合引用计数（见第九条）看每个 address 的引用数是否归零；配合 Profiler 的 Memory 面板看托管堆和各资源池的趋势。" |

## 五、地牢分帧生成：关键不是分帧，是中途退出

**30 秒版**

> 进战斗要生成整套地牢（6 间房 + 走廊 + NavGrid + 玩家 + 敌人），一口气做完会卡住主线程几百毫秒，所以我把生成改成 `async`、在 7 个位置 `await Task.Yield()`，把开销摊到约 35 帧。**但真正的重点不是 yield**：每次让出一帧后都必须检查"地牢根节点还活着吗" —— 因为玩家可能在这几十帧里按 ESC 退回主菜单，那会把整个根节点销毁；如果继续往已销毁的父节点下创建物体，那些物体会**掉到场景根、永远没人回收**，等于每局泄漏一整套地牢。

**做法**

```csharp
foreach (var r in placed)
{
    DrawRoom(r, tileFloor, tileWall);
    await Task.Yield();                    // 让出一帧
    if (Aborted(dungeonRoot)) return null; // ← 这一行才是关键
}
```

`Aborted` 用的是 Unity 的假 null 语义：被 Destroy 的对象 `== null` 为 true ✓

**追问准备**

| 面试官可能问 | 怎么答 |
| --- | --- |
| 为什么不用协程？ | "这里需要 `await` 组合多个异步步骤（资源加载、分帧生成），用 `Task` 更直观。协程也能做，但和 `async` 混用容易出现'两条时间线'。" |
| 为什么异常不会逃逸？ | "调用点是 fire-and-forget（`_ = GenerateDungeonAsync(...)`），所以方法内部整个包了 try/catch，异常只记日志，否则会变成未观测异常。" |
| 中途退出的其他资源怎么处理？ | "同一个根节点下所有东西一起销毁；资源引用走 `IAppBridge.ReleaseAsset` 成对释放。" |

## 六、热更分层：插件只能住 AOT 层，链接顺序不能反

**30 秒版**

> 项目是 AOT + 热更双程序集结构，业务全在 `CryptWalker.HotUpdate.dll`。Unity 有个硬规则：asmdef **不能引用 `Assembly-CSharp`**，而 A\* 插件默认没有 asmdef 会落到 `Assembly-CSharp` —— 所以必须用**插件自带的 asmdef**，热更侧才能 `using Pathfinding`。另一个坑是 `link.xml` 的生成时机：HybridCLR 的 `① Generate/All` 会**扫描热更程序集**自动生成 AOT 保留列表，所以必须在**调用代码写完之后**再跑 —— 反过来先跑再写代码，link.xml 里就漏掉插件，出包后热更侧调插件会被 IL2CPP 裁掉，运行时才崩。

**两个具体规则**

1. `CryptWalker.HotUpdate.asmdef` 的 `references` 里加 `AstarPathfindingProject`（程序集**边界**就是架构边界 ✓）
2. **顺序**：先写调用代码 → 再跑 `①`（生成 link.xml + 热更 dll）→ 再跑 `②` 出包

**怎么验证做对了**

```powershell
Select-String -Path "Assets/HybridCLRGenerate/link.xml" -Pattern "AstarPathfindingProject"
# → 命中 1 处 ✓ 说明 ① 是在调用代码写完之后跑的
```

**追问准备**

| 面试官可能问 | 怎么答 |
| --- | --- |
| 为什么业务要放热更层？ | "这是项目的核心卖点：**改玩法只重编热更 dll（几秒），不用重出整包（十几分钟）**。" |
| 那为什么插件不放热更层？ | "插件的代码要 IL2CPP 编进 player，热更层动不了它。**第三方库只能住 AOT**，这是分层的代价 —— 所以能自写的部分我尽量自写。" |
| link.xml 是干什么的？ | "告诉 IL2CPP 哪些类型不要裁。AOT 自动生成，因为它要扫描热更代码里用到的 AOT 类型，所以必须等代码定稿再生成。" |

## 七、免费版的能力边界：`ScanAsync` 是 Pro 功能，异常还抛穿了主流程

**30 秒版**

> 我本来想用 `ScanAsync` 做"分帧扫描"（每推进一步让出一帧），结果进战斗时地牢生成整个中断，报 `Async scanning can only be done in the pro version`。读源码发现免费版在 `AstarPath.cs:1694` 有个反作弊检查：**迭代一旦跨帧（`Time.frameCount` 变了）就抛异常** —— 也就是说"分帧扫描"被锁在 Pro 里。改用同步的 `Scan()`（它内部就是"不 yield 地遍历 `ScanAsync`"，同帧跑完）就好了。同时我补了一层：**扫描失败绝不能拖垮地牢生成**，整个扫描包 try/catch + 降级 —— 插件不可用时敌人退回自写的 A\*，游戏照常能玩。

**两个收获**

1. **免费版边界要提前查**：`Scan()` 能用、`ScanAsync()` 不能跨帧 —— 这是许可限制，不是 bug
2. **异常不能穿透主流程**：扫描失败只降级，不该让整个生成流程崩掉 ✗✓

```csharp
try { _astar.Scan(); }
catch (System.Exception e)
{
    Core.Log.Error($"[Astar] 扫描失败，寻路退回自写 A*：{e.Message}");
    _scanned = false;
    return false;
}
```

## 八、A\* 调用的取舍：为什么用同步、为什么不传回调

**30 秒版**

> 插件算路径有两种接法：传 callback 异步等，或者 `BlockUntilCalculated()` 同步等。我选同步，因为 `EnemyBase.Repath()` 原本就是"算完立刻能用"的语义，同步能保持它**一行不改**。而且**不传 callback** 意味着路径计算不会回调到热更代码 —— 跨程序集（AOT 委托 → 热更方法）和跨线程的坑一次都不碰。代价是主线程阻塞，所以我加了诊断：**每 2 秒汇报一次寻路在主线程上总共阻塞了多久**，用数据判断"卡"是不是寻路造成的，而不是靠猜。

**做法**

```csharp
var p = ABPath.Construct(from, to, null);   // 不传 callback
AstarPath.StartPath(p);
p.BlockUntilCalculated();                   // 同步等结果
result.AddRange(p.vectorPath);              // 必须拷贝：vectorPath 是 path 内部缓冲，会被池化复用
```

**关于池化**：按插件文档，**不 `Claim` 的路径不会被池化**，直接交给 GC ✓ 安全但要付一点分配成本 ✓；
想做到零 GC，照 `Seeker.OnPathComplete` 的写法加 `Claim/Release` 即可 ✓

**可观测性**：`Stopwatch.GetTimestamp()`（静态方法，零分配）累计阻塞时长，每 2 秒一条：

```
[Astar] 最近 2 秒：寻路 42 次，主线程等待共 380.0 ms（平均 9.05 ms/次）
```

> **判据**：平均 < 0.5 ms/次 → 不是寻路的问题，去别处找；几 ms 以上 → 就是它，改成异步回调版。

**追问准备**

| 面试官可能问 | 怎么答 |
| --- | --- |
| 同步阻塞不怕敌人多的时候卡吗？ | "怕，所以调用点有限流（`repathInterval`），而且我加了计量。**如果数据说明它确实是瓶颈，就换异步 —— 但先要有数据。**" |
| 为什么要拷贝 `vectorPath`？ | "它是 path 对象内部的列表，path 被池化复用时会被改写。直接存引用会被下一次寻路污染。" |

## 九、资源引用计数：`Release` 不能区分"我的"和"共享的"

**30 秒版**

> YooAsset 的 `handle.Release()` 不区分"我自己用完了"和"别人还在用"。两处业务加载同一个 address，先结束的那处一 Release 就把底层句柄销毁，另一处立刻空引用。所以我在服务层按 address 维护了引用计数：`Load` +1、`Release` −1、**归零才真正销毁句柄**，并加了 `Attach(address)` 用于"共享一份已有引用"。释放时机也有讲究 —— **先销毁实例再释放句柄**，反过来会出现"物体还在、贴图已经没了"。

**做法**

```csharp
// LoadAssetAsync 每次成功返回都占一份引用（含命中缓存的情况）
AddRef(s_assetRefCount, address);

// Release 只在归零时才真正释放
if (!DropRef(s_assetRefCount, address)) return;
handle.Release();
```

**接上有调用方的关键一处**：`UIManager.ClosePanel` —— 关闭面板时成对释放 ✗✓
包括"**加载中就关闭**"那条竞态路径（最容易漏的一条 ✓ 我也补了 ✓）

**追问准备**

| 面试官可能问 | 怎么答 |
| --- | --- |
| 为什么不直接用 YooAsset 自带的引用计数？ | "它按 AssetBundle 计数。不同 address 恰好同包时，释放 A 不应该影响 B —— 我按 address 数，语义更贴合业务。" |
| 有永久占用吗？ | "有，配置（`DataService`）是**故意**永久缓存 1 份的 —— 配置本来就该常驻。这不是泄漏，是设计。" |

## 十、日志分层：为什么用 `[Conditional]` 而不是运行时 `if`

**30 秒版**

> Release 包不想要日志，普通做法是运行时判断级别。但那样拦不住**字符串拼接** —— `Log.Info($"[X] {a}{b}")` 里的 `$""` 在调用之前就算完了，所以哪怕不输出，热路径照样每帧产 GC 垃圾。正确做法是 `[Conditional]` 特性：它是**编译期行为**，整个调用表达式一起被删掉，零开销。同时 `Warn` / `Error` **故意不加** —— 它们频率低，而且通常意味着"配置错了"，恰恰是线上最需要看到的线索。

**做法**

```csharp
[Conditional("DEBUG")]
[Conditional("UNITY_EDITOR")]
public static void Info(string message) => _bridge?.Log(LogLevel.Info, message);

public static void Warn(string message)  => _bridge?.Log(LogLevel.Warn, message);   // 不加：保留
```

**顺手做的一件事**：审计了全工程"日志参数里带方法调用"的地方（3 处），确认都是纯读 ✓
因为 `[Conditional]` 有个**使用纪律**：不能在日志参数里写有副作用的表达式 —— `Debug` 下执行、Release 下不执行，语义就变了 ✗

**追问准备**

| 面试官可能问 | 怎么答 |
| --- | --- |
| `[Conditional]` 和 `#if` 的区别？ | "`#if` 是源码级、要把调用点包起来；`[Conditional]` 是方法级、调用点写法不变，编译器负责剔除。**改一处定义即可全工程生效。**" |
| 为什么 `Warn` 不剔除？ | "剔除等于让线上排查变瞎。日志分层的原则是：**高频信息剔除，低频线索保留。**" |

## 十一、让程序适配美术的随手摆放：嵌套层级 + 进度条方向

**30 秒版**

> 加载面板是美术做的，我先用 `transform.Find("Img_blue")` 找控件 —— **只找到三个里的一个**。原因是 `transform.Find` 只查直接子物体，而那两个控件嵌在背景图下面一层。改成递归查找。另外那个进度条的 `Image` 类型是 `Sliced` 而不是 `Filled`，不能用 `fillAmount`，得靠**改宽度**；而改宽度朝哪边长由 `pivot` 决定 —— 与其要求美术把 pivot 设成 0，我在代码里**按 pivot 反算 anchoredPosition 把左边缘锁死**，这样不管美术怎么摆，进度条都从左往右长。

**两条工程习惯**

1. **找控件要递归**，并在找不到时**把真实层级打出来**（自诊断 ✗✓）：
   ```csharp
   Debug.LogWarning($"...下面是面板的真实层级：\n{DumpHierarchy(panel.transform)}");
   ```
2. **对外部布局做补偿，而不是提要求**：
   ```csharp
   _barLeftEdgeX = _bar.anchoredPosition.x - _bar.pivot.x * _bar.sizeDelta.x;   // 记下左边缘
   pos.x = _barLeftEdgeX + _barPivot.x * size.x;                               // 改宽度时锁回去
   ```

## 十三、面试官问"你怎么定位问题的"（方法论总结）

如果被问到这道**元问题**，按这个顺序答：

1. **先让数据说话，别先读代码猜**
   —— 给关键数据加**等值断言**（"这两边必须相等"）。第一、二条 bug 都是这么抓出来的 ✓

2. **数字"两头不靠"就是指纹**
   —— `5183` 既不等于 `8541` 也不等于 `1587` ✓ → 说明是**坐标塌陷**，不是偏移 ✓
   数字模式能直接指向 bug 的类型 ✗✓

3. **从"时间点/边界"推责任方**
   —— "Loading **之后**才卡" → 找"加载完还在跑的东西" ✓

4. **改完要回核被保护的不变量**
   —— 第二版修贴墙时，我回核了"可走数" ✓ → 才发现走廊被堵 ✓
   **修 bug 前先写清"哪些东西不能被破坏"** ✓

5. **把不可见的抖动挪到可见的地方**
   —— GC、扫描耗时（227 ms）都塞进加载界面 ✓

6. **每个修复都要有可验证的判据**
   —— 修完要打出 `✓ 一致`、`1587/1587`、`改动 6954 个` 这种**能反证的数字**，而不是"感觉好了" ✗✓
   说"感觉好了"的修复，下次同一个 bug 换个样子回来你照样认不出来 ✗
